THE BUILDING BLOCKS

Event → Slot → Invitation → Booking

Bookign system is built from four basic connected layers.

1

Event

The container for everything. Holds basic event info, event location (with map), event booking rules, and — most importantly — a type that determines how its slots behave.

2

Slots

Created inside an event, slots define when bookings can happen. Holds basic slot info, slot booking rules, slot bookable time. Their shape depends entirely on the chosen event type.

3

Invitation

A shareable link tied to an event, with one or more slots attached. This is what gets sent to attendees to book against.

4

Booking

Storage for all booking info, where booking info can be traced back by organizer and attendee.

THREE FLAVORS OF SCHEDULING

Choose the event type that fits

The event type changes how organizers configure availability — and how attendees pick their time.

Business

Child slot will be set as recurring weekly hours — great for clinics, salons, support slots etc.

  • Set your weekly business hours — e.g. Mon–Fri 9am–5pm
  • Define a frequency — e.g. every 5 minutes
  • Define a duration per booking — e.g. 1 hour
  • Attendee picks a start time → booking blocks that window automatically — e.g. attendee pick 4:15pm, booking blocks time frame for 4.15pm-5.15pm
Example: walk-in consultation slots

Flexible

Child slot will be set as custom availability windows — great for tutoring, freelance calls, interviews etc.

  • Define one or multiple date + time ranges — e.g. Date A 8am–3pm, Date B 11am–12pm
  • Same frequency & duration controls as Business
  • One slot can be sent to multiple invitees — each picks their own time independently
Example: 1-on-1 tuition with 5 students sharing one slot pool

Fixed

Child slot will be set with a single, fixed start and end time — ideal for webinars, group sessions, set appointments etc.

  • Organizer sets one fixed start & end time
  • Attendees book directly against that exact slot
  • No frequency/duration math — what you set is what's booked
Example: a live group workshop at a set date & time

An invitation can attach multiple slots within the same event.

Three-layer booking limits

Organizers can cap how many times a single identity can book — enforced at three independent layers:

Event
Slot
Invitation

Each layer can define its own per-identity limit, giving organizers fine-grained control over how often the same person can book.

Email notifications

Automated emails keep everyone in sync:

  • Organizer get notified when someone books a slot
  • Organizer get notified when an attendee cancels
  • Attendee get booking details when succesfully books a slot
  • Attendee get notified if the organizer cancels their booking
UNDER THE HOOD

Architecture & stack

Built and deployed across separate managed services.

Frontend Angular · Vercel
Backend Spring Boot · Render
Database PostgreSQL · Neon
Cache Redis · Upstash

Backend

  • Spring Boot as the core framework
  • Spring Data JPA for database access
  • Redis caching layer for read-heavy endpoints, with event-scoped cache invalidation on writes
  • JWT authentication for registered users
  • Sensitive public endpoints (view/create/delete booking) protected with short-lived temporary JWT tokens
  • Every service method protected via @PreAuthorize
  • Global error-handling interceptor for consistent API responses
  • IP-based security bouncer filter for request filtering
  • Risk scoring service that evaluates failed attempts and dynamically triggers reCAPTCHA challenges
  • Transactional boundaries @Transactional to ensures correctness after execution
  • Database-level locking with @Lock(PESSIMISTIC_WRITE) to prevent slot overbooking, exceeding invitation limits, and ensure consistency during concurrent booking operations
  • Bean Validation @Valid and Custom Validator to prevents invalid data from entering service layer

Frontend

  • Angular with a component-based structure mirroring the UI
  • FullCalendar for slot & booking visualization
  • Leaflet for event location maps
  • Bootstrap + Font Awesome for UI & icons
  • Modern Angular Signals and classic Angular lifecycle are used to implement a reactive UI experience
  • Global HTTP error interceptor for consistent error handling
  • Auth interceptor attaches the appropriate JWT token per request based on route context
  • Route guards for authentication and authorization control
  • Conditional reCAPTCHA rendering based on backend risk signals
  • Centralized API service layer for structured backend communication
  • Global loading service to improve UI experience
  • Structured logging system with multiple severity levels (INFO, WARN, ERROR, DEBUG) for monitoring and debugging
  • Centralized error mapping service that normalizes backend HTTP errors into a unified format and maps standardized error codes to user-friendly messages
  • Standardized error code contract shared between backend and frontend for consistent system-wide error handling
